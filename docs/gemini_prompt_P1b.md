# Gemini 向け指示書: P1b（ペース再調整）

P1 の実装（`dev` ブランチ e1d183d）の検証で、「周回がほぼ不要になり、遊ぶ時間が大幅に短くなった」ことが分かった。その修正指示。P1 の実装内容（難易度・セーブv3・ドロップ上限・★6・戦力値・ゴールドの使い道・テスト）は**そのまま残し**、ペース（EXP・敵の強さ・階数）だけ作り直す。

## 【プロンプト本文（ここから貼り付け）】

あなたは、ブラウザで動くローグライクRPG「rogue-demo」の開発担当エンジニアです。リポジトリ `ToMoreKey/rogue-demo` の `dev` ブランチ（**最新を取得してから**）で、下記の「P1b ペース再調整」を実装してください。回答と報告は日本語で、簡潔にお願いします。

### 0. 経緯と、直したい問題
P1 の検証結果（`python3 tools/bot.py` の周回モード）:

| | P1 前（9セル） | P1 後（15セル） |
|---|---|---|
| ラン数 | 91〜95 | 17〜19 |
| 終了時Lv | 31 | 58〜65 |
| 戦闘（4倍速換算） | 約11分 | 約3.4〜4.2分 |
| 敗北 | 0〜4回 | 0〜1回 |

- 難易度ごとのEXP倍率（`expMult` 2.8〜6.2）と、下げた `expNeed` のせいで、レベルが急に上がり、周回が不要になった。デバッグ部隊の指摘は「EXPが多すぎる」だったので、**逆方向になっている**。
- 1階あたり約4ティックで、敵がほぼ一撃で倒れ、手応えが落ちている。
- P1 の合格基準（「各セル1回ずつ挑み、レベル差が −3〜+2」）が、周回しなくてよい調整を合格にしていた。**この基準は撤回する**（私の指示の誤り）。

### 1. 時間の見積もりモデル（これを基準にする）
デバッグ部隊の実測: 1ランが4倍速でおよそ30秒。全制覇（9セル）が約2時間＝約91ラン。

**人間の所要時間（4倍速）≒ 通過した階数 × 2.5秒 ＋ ラン数 × 50秒**

- 通過した階数は、周回・敗北・撤退を含め、実際に進んだ階の合計。
- 方針（決定済み・`docs/spec_volume_expansion.md` の「時間の見積もりモデル」）: **1ランを長くする**。1セルの周回は平均4〜6ラン。EXPは現状より低めにし、手応え（1階あたりの戦闘の長さ）は変えない。

### 2. 前提（これまでと同じ）
- `src/` を編集し、`python3 tools/build.py` で `index.html` を生成する。`index.html` を直接編集しない。
- `window.__rogue` と `window.G` を残す。画像・配色は触らない。外部ライブラリを追加しない。
- 作業は `dev` ブランチ。`main` には push しない。push は P0・P1 と同じ方法（トークンは設定ファイルから読み、その場の変数で使い、画面・ログ・報告・ファイルに出さない。使用後に変数を破棄）。
- `index.html` を更新したら、`sw.js` の `CACHE` のバージョンを上げる。

### 3. やること

#### 3-1. BOTに所要時間モデルを入れる
- `tools/bot.py` に、通過した階数（`floorsTraversed`）を数える処理を足す。
- 結果の出力に `model_minutes`（= 通過階数×2.5秒 + ラン数×50秒 を分に直した値）と `model_hours` を足す。既存の出力は残す。
- **P1 前の挙動を基準値として記録する**: 変更前の版（コミット `1da3ff6` のビルド。`git worktree` などで別に取得）で、A〜C×初級〜上級（9セル）を同じBOTで測り、**1階あたりの平均ティック数**と、ラン数・通過階数・`model_hours` を `docs/dev_notes_P1.md` に表で残す。これを「手応えの基準」にする。

#### 3-2. 階数の変更
- 超級を **50階**、極級を **80階** にする（`DIFFS.floors`）。初級・中級・上級は5/10/20のまま。
- 階数が長いランのため、**10階ごとに「節目の強敵」**を出す（最終階のボスとは別）。既存の雑魚またはボスの上位種（同じ画像・色味とステータスの差）を使い、新しい画像は使わない。出現・報酬は既存の仕組みに合わせる。
- 階数に比例して、1ランあたりの報酬（`clearGold` `clearSp` など）が極端に増えないよう確認する。

#### 3-3. EXPと敵の強さの再調整
次の方針で、`expNeed`・難易度ごとの `expMult`・`pow`・敵のステータスを調整する。
- **EXPは、P1 前の同じ条件より低め**にする。「同じセルを、レベルが推奨に届くまでに平均4〜6ラン」かかる程度。
- **敵の強さ（1階あたりの戦闘の長さ）は、3-1 で測った基準と同程度**（基準の ±25% 以内）にする。レベルが上がっても戦闘が一撃で終わらないよう、`pow` を調整する。
- 極級まで通して、終了時のレベルは Lv56〜60 付近（A〜Cの範囲）。

#### 3-4. 合格基準（BOTで測る）
周回モード（既存。「推奨レベルに届くまで下を周回する」方針）で、3シードすべて次を満たす。
1. 全15セルをクリアできる（`done: true`）。
2. `model_hours` が **3.5〜4.5時間**。
3. ラン数が **70〜100**（平均で1セルあたり約5ラン）。
4. 初回挑戦でのクリア率が **70%以上**、敗北は全ランの **15%以下**。
5. 1階あたりの平均ティック数が、3-1 の基準値の **±25% 以内**。
6. 終了時レベルが **Lv56〜60** 付近。
7. 余りゴールドが約7万G以下（P1 の基準を維持）。

線形モード（各セル1回ずつ）は、「ダンジョンの順番に進めるだけではレベルが足りず、周回が必要になる」ことの確認に使う。レベル差が **推奨より −4以下のセルが半数以上**になることを確認し、結果を報告する（P1 の「−3〜+2」は撤回）。

#### 3-5. テスト
- 既存のテスト（`test_p1.py` `test_save_migration.py`）がすべて通ること。階数変更で壊れたものは直す。
- `python3 tools/build.py` が再現可能であること。
- 80階のランが、画面・パフォーマンスの面で問題なく動くこと（フロアの表示 `pip` が420px幅で崩れない、メモリ・処理が重くならない）。必要なら、階数表示を省略表示（例: 「42 / 80」）にする。
