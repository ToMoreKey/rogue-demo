# 変更書: P9（ゲーム内の不具合報告）

## 1. 目的
プレイヤーがゲーム内から不具合・バランス・要望を報告でき、報告が蓄積され、運営者が定期的にまとめて対策できるようにする。運営者承認（2026-11-22、推奨案）。運用は `docs/bugreport_setup.md`。

## 2. 仕組み
ゲーム → （同意したうえで）Googleフォームの `formResponse` に送信（ランキングと同じ方式）→ スプレッドシート → 運営者がCSVで書き出し → `tools/make_bug_report.py` で対策リスト化。外部サーバー・トークンは使わない。

## 3. ゲーム内の機能
### 3-1. 入口
- ヘルプ画面の下部と、ステータス画面の「データ」パネルに、「不具合・ご意見を送る」ボタンを置く（目立ちすぎない、既存のボタンと同じ大きさ）。

### 3-2. 報告画面（モーダル）
- 種類（選択）: 不具合 / バランス / 要望 / その他。
- 内容（複数行、必須、5〜500文字。文字数カウンターを表示）。入力欄の下に「どの画面で何を押したか、書いてもらえると助かります」と案内する。
- 送られる診断情報を、**そのまま表示**する（読み取り専用）。
- 同意チェック（必須）: 「内容と診断情報（セーブデータ・名前は含みません）を送信することに同意します」。チェックするまで送信ボタンは押せない。
- 送信ボタン／キャンセル。下端のボタンは常に見える位置に置く（`.sheet>.act:last-child` の既存の仕組みを使う）。

### 3-3. 診断情報（1行の文字列。`キー=値` を `; ` で区切る）
`build=prod|dev; ver=<版>; vp=<幅>x<高さ>; ua=<ブラウザ名とOS名のみ>; lv=<レベル>; dg=<ダンジョンID or ->; fl=<階 or ->; view=<開いている画面>; err=<直近の画面エラー最大3件を | で区切る>`
- `build`: `IS_DEV_BUILD` から決める。
- `ver`: `sw.js` の `CACHE` 名（例 `rogue-v34`）。`tools/build.py` がビルド時に `sw.js` から読み取り、定数 `APP_VERSION` に埋める（本番とテスト版で `rogue-dev-vN`）。手で書き換えない。
- `ua`: ユーザーエージェントの全文は送らない。ブラウザ名（Chrome/Safari/Firefox/Edge）とOS名（Android/iOS/Windows/macOS/Linux）だけにする。
- `err`: `window.onerror` と `unhandledrejection` を起動時から拾い、直近3件（メッセージ120文字まで＋ファイル名と行番号）を保持する。URL・個人情報になりうる文字列は含めない。
- **送らないもの**: セーブデータ、ニックネーム、ランキング同意の状態、所持品、メールアドレスなどの個人情報。

### 3-4. 送信
- `fetch(reportUrl, { method: 'POST', mode: 'no-cors', body: FormData })`。成功は確認できないため、画面には「送信しました。ありがとうございます」と出す（ネットワーク失敗は検出できた場合だけ失敗扱い）。
- 連続送信は60秒に1回まで。待ち時間中は押せない理由を表示する。
- 通信できない場合（オフライン・失敗）は、端末に保存（`localStorage`、最大5件）し、次回起動時とオンライン復帰時に再送する。再送の成功確認はしない（送信済みとして消す）。
- 設定が未入力（`reportUrl` が空）のときは、ボタンは出すが、画面に「準備中です」と表示して送信できない。
- 設定値は `src/data/bugreport.js` の `BUGREPORT_CFG`（`reportUrl`、`entryKind`、`entryText`、`entryDiag`、`rateLimitSec`、`textMin`、`textMax`、`queueKey`）に置く。**キー名は `reportUrl` にする**（ランキングの `formUrl` と置換が混ざらないようにするため）。値は運営者がフォームを作ったあとに入れる（`docs/bugreport_setup.md` のD）。

### 3-5. 本番とテスト版
- テスト版（`/dev/`）でも送信できる（診断情報の `build=dev` で本番と区別する）。ランキングと違い、無効にしない。
- 再送キューの保存キーは、テスト版では `rogue_dev_` 系に分ける（`tools/build.py` の `to_dev` に置換を追加し、`tools/test_variants.py` に確認を足す）。

## 4. 守ること
- ゲームの数値・バランス・BOT結果、セーブ形式（v8）は変えない。送信キューは別キーに置く。
- 秘密情報（トークン等）をゲームに入れない。フォームURLと質問IDは公開してよい値。
- 外部ライブラリを追加しない。420pxで崩れない。既存のテスト（`test_p1`〜最新、`test_save_migration`、`test_variants`、`test_noskip`、`test_p8`、`test_modal_close`、`test_layout`）が OK。

## 5. 合格基準
1. 入口2か所から報告画面が開く。同意チェック前は送信できない。内容が5文字未満・500文字超は送信できない。
2. 診断情報が仕様どおり（キー、ブラウザ名/OS名のみ、`err` は最大3件・120文字まで）。セーブデータ・名前が含まれない（テストでキー名と値を検査する）。
3. 送信が `formResponse` へ、正しい `entry.*` と値で行われる（Playwright で通信を傍受して確認）。連続送信は60秒に1回まで。
4. オフライン時にキューに保存され、オンライン復帰または次回起動で再送される。キューは最大5件。
5. `reportUrl` が空のとき、「準備中」で送信できない。
6. 本番ビルドとテスト版ビルドで、キーと `build=` が分かれる（`test_variants.py`）。
7. `tools/make_bug_report.py` に、ゲームが出す診断情報をそのまま食わせて、正しく集計できる（`test_p9.py` に含める）。
